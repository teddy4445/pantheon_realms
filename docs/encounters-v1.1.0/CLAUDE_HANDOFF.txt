1. HERO MEETING SCENE
Current component: packages/ui/src/dialogs/Overlays.tsx, TransferDialog.
Current state supports hero-to-hero and hero-to-town-garrison transfer. The scene is a visual upgrade of that component, not a new diplomacy, hiring or artifact-trading mechanic.

COMPOSITION
- Choose encounterkit.meeting.<initiating hero's pantheon>. This is decorative camp scenery, not an exact depiction of the current tile or a new world location. For mixed-pantheon meetings the initiating side chooses the camp; each hero keeps their actual identity and emblem.
- Keep the existing heading and a short instruction above the scene. Put each real hero's bust above their corresponding troop strip. Keep names and counts in live HTML.
- Resolve each hero's actual portraitAssetId from the catalog/state. Follow the existing storyArt.ts convention: replace the ending .portrait with .bust and resolveArt. hero-art-map.json enumerates available pairs. Use existing alphaBox/layout metadata where present. If no bust exists, use that SAME hero's portrait inside the supplied socket. Do not pick a random hero of the same faction.
- Existing speakerSides documents busts facing right. Mirror the RIGHT display layer with CSS, as current dialogue scenes do, when appropriate to that bust. Do not reverse lettering or asymmetric identity-critical details if a future asset includes them. No raster edits required.
- Use the current ArmyStrip and actual army.slots array. Preserve every slot even when empty. The demo shows seven positions; bind the game array rather than hardcoding a replacement inventory size.
- On desktop, two troop strips side by side under their respective heroes. Keep the fire visible between them. On smaller screens wrap each strip and reduce portrait height; retain clear source/destination labels. At very narrow widths stack the two armies if necessary, preserving every slot and all controls. Portraits must never cover buttons.
- Garrison mode: show the actual town name and appropriate existing town art in place of a second hero. Do not invent a castellan. Label it explicitly as a garrison. The target inventory remains town.garrison.

BEHAVIOR TO PRESERVE
TransferDialog currently selects a source slot, optionally chooses a quantity, calls quoteTransfer against the current state, and dispatches TransferStack on destination click. Same-slot click clears selection. Matching stacks merge and other legal operations follow quoteTransfer. A hero must retain at least one creature. Do not duplicate validation with guessed UI rules. Errors need readable feedback.
Keep immediate destination-click commit. Done only closes the meeting; it is not an Apply button. Cancel clears the pending source/quantity only and must not pretend to undo a transfer already committed. Do not add a second command when a drop animation finishes. If drag/drop is added, preserve click and keyboard alternatives and route both through the same command path exactly once.
The demo only shows selection/quantity/destination feedback; it is NOT a transfer-rules implementation. Retain real merge, swap, split, ownership, adjacency and garrison validation in the game.

MOTION
A subtle 150–220ms source/target highlight is sufficient. Avoid moving the portraits during normal selection. No looping zoom, camera rotation or large fire effects. Honor reduced motion with immediate state changes. Existing backgrounds contain static painted fire; an optional low-opacity CSS glow must not imply an animated video asset was delivered.

COMPOSITION AND ASSET BINDING

- Resources use icon.res.<key> and actual localized amounts. Existing keys are gold, wood, stone, crystal and favor; do not introduce Gems or Ore just because Heroes III uses them.
- XP uses icon.stat.xp; mana and movement use icon.stat.mana and icon.stat.movement. Attributes use icon.stat.attack/defense/power/knowledge.
- Artifacts use catalog.artifacts[id].iconAssetId, name and actual awarded location. If ArtifactGranted.location is cache, say where it went; never always label it 'In your backpack'. The example ring is only sample content.
- Creatures use catalog.creatures[id].presentation.portraitAssetId and actual count. Entitlements use the existing gift icon and the real entitlement name/description. Special unlocks may use a matching existing icon if available; do not fabricate rewards.
- Show positive outcomes in the tray, costs in a separate line, and partial/capped outcomes accurately. Zero-reward and already-claimed cases must not show celebratory fake items. XP should show the actual granted amount and cap message when applicable.

COMMITTED DATA, EXACTLY ONCE

Avoid counting both a summary event and its detailed grant events as separate gains. Never parse success-toast prose to reconstruct rewards.

Reuse an existing event-consumption mechanism if available. Add UI state only where required; do not change rule outcomes to drive artwork.
