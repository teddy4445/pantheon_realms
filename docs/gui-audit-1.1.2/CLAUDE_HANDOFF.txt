FIX 1 — SIEGE GATE ORIENTATION, REGISTRATION AND BREACH (HIGH PRIORITY)
Evidence: siege-after-<pantheon>.png shows the existing 1.1.2 implementation. Its broad gatehouse faces a different direction from the narrow vertical wall and horizontal bridge. It reads as a separate miniature building, not an opening in the wall.
The new gate faces screen-left (the attackers), with north/south wall connectors and a screen-left-to-right passage. There are six independent faction atlases and three states each: intact, damaged, rubble/breached. The final selected files are gate.greek-v5.png, gate.norse-v5.png, gate.egyptian-v5.png, gate.japanese-v5.png, gate.celtic-v5.png and gate.mesoamerican-v5.png. Earlier revisions are drafts; do not register them.
All six are native 1536 x 1024 RGBA PNGs, three 512 x 1024 frames across. No upscaling, code retouching or baked ground was used. The v5 suffix is an artwork revision, not a game version. The pack folder remains siege-gates-v3 to distinguish this gate-only delivery from the previously integrated siege-v2 environment pack.

Implementation entry points:
  packages/ui/src/assets/manifest.ts — currently imports siege-v2/manifest.json and spreads SIEGE_V2.siege into registerSpriteManifest.
  packages/presentation/src/battle.ts — siegeDef / drawStructures select HP-state sprites and place gate, tower and keep art.
  packages/presentation/src/siegeLayout.ts — siegeWallPoint, siegeSpan, SIEGE_HEX and SIEGE_ROW.
  packages/presentation/src/sprites.ts — StaticSpriteDefinition frame, anchor and pixelsPerHex.
Import the new manifest and spread its .siege LAST after existing siege sprite mappings. It contains ONLY 18 gate keys, gate.intact.<pantheon>, gate.damaged.<pantheon>, gate.rubble.<pantheon>. Keep v2 backgrounds, walls, towers, keep, palette and ground system.

Minimal registration sketch for packages/ui/src/assets/manifest.ts:
  import siegeGateV3 from '../../../../assets-runtime/siege-gates-v3/manifest.json';
  const GATE_V3 = siegeGateV3 as unknown as { siege: SpriteManifest['siege'] };
  // Inside the existing registerSpriteManifest object:
  siege: {
    ...(spriteManifestFile as unknown as SpriteManifest).siege,
    ...SIEGE_V2.siege,
    ...GATE_V3.siege,
  }
Keep the existing relative asset resolver and surrounding registration fields. This is a patch sketch, not a replacement for the entire manifest module.
Use the supplied individual frame rectangles and anchors. The drawings are not equally centered inside their cells; do NOT replace every anchor with [0.5, 0.5]. Do not auto-trim each damage state and then recenter its silhouette: this makes the gate jump as HP changes. Register the north wall axis and passage center, as recorded in manifest.json.
The supplied scale is a starting fit tested with the current renderer, not permission to ignore joins. At current constants SIEGE_RADIUS=40, SIEGE_HEX is about 69.282 and SIEGE_ROW is 44.4. Anchor the passage at siegeWallPoint(wallCol, gateRow). Derive bridge, road, wall and gate placement from that same gate row. Adjust presentation offsets if needed; never move the combat cells to fit a painting.
Render ground/road below the structure. Keep a visible continuous approach from bridge to doorway and onward into the town. The new atlases deliberately have no bridge or ground plane. Do not put a second bridge into the sprite. Avoid drawing intact wall fill across the breached gate cell. Keep debris to the north/south ends. A destroyed gate must look traversable in the same place where the rules permit passage.
Gate connector tails overlap adjoining wall art. Restrict that decorative overlap when an adjacent wall section is destroyed, so a gate tail cannot visually restore a destroyed neighbor. This is a renderer clipping/section-ownership requirement, not a change to siege HP or pathfinding. Check depth sorting with units passing behind the near jamb and in front of the far jamb. Keep selection, target overlays and movement preview readable.
Reuse the existing HP-state thresholds. Verify full HP = intact, nonzero damaged HP = damaged, zero HP = rubble, and that loading a save preserves those states. Do not infer HP from the displayed image.
The siege-prototype-* images are isolated browser previews of manifest substitution and staged HP changes, NOT screenshots of an implemented source change. They help review scale/orientation; final acceptance still includes movement through the breach and adjacent wall destruction.

FIX 2 — START BATTLE LABEL CLIPPED BY ITS PAINTED BUTTON (HIGH PRIORITY)
Evidence: siege-after-greek.png, bottom center; repeated across the faction siege captures at 1600 x 1000. The icon is visible while the text descends into/out of the bottom painted edge.
Inspect packages/ui/src/screens/Battle.tsx battle-actions / deploy-confirm, packages/ui/src/styles/screens.css battle tile-button sizing, and packages/ui/src/styles/gui.css .btn--primary. The primary face is 2.4rem while the battle tile stacks a large icon plus text. The adventure footer's separate 1.1.2 adjustment does not resolve this battle context.
Give the deployment action a horizontal icon-and-label layout, or make its painted face and footer tall enough for the vertical contents. Center text within the actual painted face, not the transparent outer pixels. Preserve an accessible hit target of at least 44px, focus indication, keyboard activation and disabled state. Check the other battle commands for the same conflict. Existing button art is sufficient; no new button PNG is needed.

FIX 3 — PARCHMENT LABEL CONTRAST (MEDIUM PRIORITY)
Evidence: screenshots/S03A.png and screenshots/campaign-confirmed.png, the Difficulty label on the parchment mission pane. Computed text is rgb(245,228,183), close to the parchment color (see focus-evidence.json).

Check campaign, skirmish map details and random-map settings using the same shared label. Normal-sized text should meet 4.5:1 contrast. Do not globally turn all labels dark.

FIX 4 — READABLE COLD-LOAD / FAILED-IMAGE FALLBACK (MEDIUM PRIORITY)
The Journal's finished layout is CORRECT. screenshots/journal-decoded.png proves the book and mission art decode and fit the two-page layout. Do not rebuild or replace this book.
However, screenshots/journal-confirmed.png and journal-narrow.png capture dark ink exposed directly on the dark background before the parchment image arrived. This was especially visible under load. A later explicit image decode resolved it (journal-asset-check.json). It is a loading/fallback problem, not a permanently missing file.
In packages/ui/src/components/gui.tsx Folio and packages/ui/src/styles/gui.css, give text-bearing page rectangles a readable parchment-color fallback while the book is pending or failed. Preload/decode critical UI skins through the existing asset resolver before exposing ink-on-parchment content; fade the decorative art in when ready. Prefer a styled fallback to hiding all objectives behind a spinner. A failed background image must never leave low-contrast text. Do the same for similar codex/dialog surfaces.
Test both cold load and an intentionally failed book request. Preserve narrow-width stacking, page scrolling and focus. Existing assets-runtime/ui-v1.1.0/book-open.png is valid 1536 x 1024 and should be reused. No replacement book raster is required.
